# Corrections and falsifications — 1brc

Per `spec.md:41`: a published number or claim later found wrong is corrected at EVERY site that publishes it, and gets one entry here. Empty is a valid state; it means nothing published was later disproved. A non-empty file is not an embarrassment, it is the part of the record that proves the rest was checked.

One entry per falsified claim: what was claimed, where it was published, what disproved it, and the commit that corrected it.

---

## C1 — "88.6% of station names are longer than 8 bytes"

- **Claimed:** that 88.6% of the 413 official station names exceed 8 bytes, offered as the rationale for hypothesis H2 (a 16-byte NEON compare should beat an 8-byte SWAR word on the name scan).
- **Published in:** a draft of `03-technique-recon.md`, in the H2 paragraph. Caught before the commit landed, so it never reached a pushed commit.
- **What disproved it:** direct computation over the key table in `code/gen/stations.go`, recorded as probe 5 in `03-technique-recon-data.txt`. Measured: **34.1%** longer than 8 bytes (141 of 413), mean 8.0 bytes, max 26 (`Las Palmas de Gran Canaria`), and only 1.0% longer than 16 bytes. The claim was wrong by a factor of 2.6.
- **Why it happened:** the figure was invented to support a hypothesis that felt right, in a file whose whole purpose is to hold checkable claims. Nothing measured it, and nothing had to: the key set is 413 rows in a file already in the repo.
- **Consequence:** H2's prediction changed direction. It had been "NEON wins on names"; it now says the margin may go either way, because SWAR's second load is an L1 hit while NEON pays a vector-to-general-register transfer on every row. The correction also surfaced a fact the wrong number hid: 1.0% of names exceed 16 bytes, so thomaswue's 16-byte hash window has a slow path that fires on ~1% of rows rather than never.
- **Corrected in:** `61dcbb6` (report and data companion, same commit as the claim).

## C2 — "under 1.0 s wall clock, warm page cache" as the stated target

- **Claimed:** that our target is 1B rows in under 1.0 s with a **warm page cache**, mirroring the official eval's method.
- **Published in:** `01-definition.md:91` (the "our target" paragraph), and the corresponding rule in `spec.md:35` as originally written.
- **What disproved it:** `02-baseline.md` / `02-baseline-data.txt`. The 1b file is 13,795,610,267 bytes = 12.85 GiB, which is 53.5% of this machine's 24.00 GiB. After two full sequential passes, free memory is 57.8 MiB and only 9.47 GiB sits on the active+inactive lists: macOS evicts the head of the file while the tail is being read, so the warm-cache state is not reachable here at all. Worse for the premise, the page-cached path is **slower** than an uncached one — 1.126 s ± 0.007 s page-cached against 754.4 ms ± 8.8 ms with `F_NOCACHE` and 15 parallel readers, a 1.49x inversion of the usual assumption.
- **Consequence:** the target is a wall clock under a **named, reproducible storage state**, not under a state this machine cannot enter. `spec.md:35` was amended accordingly by the operator, and every published number now names its storage state and reader configuration.
- **Corrected in:** this commit (`01-definition.md` at its site); the rule itself in the operator's `9c9aded`.

## C3 — "the batch tokenizer is worth −42.3% on the official key set"

- **Claimed:** that gigatoken's batch shape tokenizes the 413-station corpus at **6.475 ns/row against staged SWAR's 11.225, −42.3%**, published as the largest win measured anywhere in this study and as the shape `go-v1-parallel` should start from.
- **Published in:** `04-asm-kernels.md` (the headline table, the H2 rescue sentence, the batch section, the hands-forward table and the threads list), `04-asm-kernels-data.txt` (medians and deltas), and `docs/1brc/built.md` — all in commit `b4be167`, which was pushed.
- **What disproved it:** the review gate on the same group. The number is a correct measurement of a kernel that was **wrong**: `TokenizeBatch` overwrote its pending separator on every `;` it drained, so it ended a name at the LAST separator in a row while `TokenizeScalar`, `TokenizeStagedSWAR` and `TokenizeStagedNEON` all end it at the first, which is `gen.Aggregate`'s rule. On `Ab;cd;1.0` the batch kernel reported a 5-byte name and the others a 2-byte one, so it would have attributed the row to a different station. Neither key set produces a name containing `;`, so `TestTokenizersMatchTheScalarReference` and `TestBatchBenchLoopCoversEveryRow` both passed over both corpora with the bug present — the benchmark was pricing work the kernel was not doing correctly.
- **Measured after the repair:** **−40.4%** (6.253 against 10.490) and **−40.7%** (6.367 against 10.735) in two post-fix runs, both disjoint over ten runs each. The verdict survives; the magnitude drops by about 1.8 points, which is the one predictable branch the repair adds to the drain loop. The 10k crossover also survives in direction (+13.8% and +12.1%) but its ranges overlap in the noisier of the two runs, so it is now reported as a reproduced direction rather than a separated margin.
- **Why it happened:** the kernel was checked only against inputs the generator can produce. The repo already knew this failure mode — `docs/1brc/lessons.md` records the identical first-vs-last-`;` divergence being caught in `go-skeleton` one group earlier, by mutation testing rather than by the corpus — and the batch kernel was written afterwards without the guard.
- **Corrected in:** `730d166` (the kernel, plus `TestEveryKernelEndsTheNameAtTheFIRSTSemicolon`, which fails when the guard is reverted while the corpus agreement tests still pass), and this commit at every site above.

## C4 — "a `1<<17` entry array is 4 MiB, and splitting it out shrinks the probed array 4x"

- **Claimed:** that the per-shard table's `entry` is 32 bytes, so a `1<<17` entry array is 4 MiB and a `1<<14` one is 512 KiB, and that H5's separate 8-byte hash array therefore touches "a quarter" as much memory.
- **Published in:** `07-experiment-ledger.md` E-03's idea and prediction lines and E-07's prediction line, `05-go-techniques.md` (the working-set hypothesis and the hands-forward table), `1brc/code/go/table.go`'s `table` doc comment, and `docs/1brc/handoff.md`'s `go-recon` deviations line.
- **What disproved it:** `unsafe.Sizeof(entry{})` on this machine, recorded with its throwaway test in `06-cross-disciplinary-transfer-data.txt` §2. `entry` is **48 bytes**, not 32: `key []byte` is a 24-byte slice header on arm64, plus `min`/`max` int32, `sum` int64 and `count` int32 is 44, padded to 48 by `sum`'s alignment. So a `1<<17` array is **6.00 MiB**, a `1<<14` array is **768 KiB**, and the split-array ratio is **6x**, not 4x.
- **Consequence for the verdicts: none, and that is worth stating.** E-03's split layout still lost 4.6% at 413 stations and E-07's big table still won 7.2%; both were measured, and only the arithmetic *around* them was wrong. The correction makes E-03's mechanism argument stronger, not weaker, which is exactly why it needed catching: a number that supports your conclusion is the one nobody re-checks.
- **Why it happened:** the size was computed by counting the fields' logical widths and never checked against the compiler. `24 + 4 + 4 + 8 + 4` was read as "about 32" because four fields are 4 or 8 bytes and the slice header was counted as a pointer.
- **Corrected in:** this commit, at all six sites, each marked inline. `docs/1brc/handoff.md`'s copy is corrected in this cycle's own handoff block rather than by editing the historical block, which the handoff protocol writes before its review.

## C5 — "a 1-billion-row 10,000-station file is ~20 s of generation"

- **Claimed:** that queue item 8, the 1b 10k-station file that E-03's parked half and hypotheses H-12, H-13, P-03 and queue items 9 and 10 all depend on, costs about 20 seconds to generate, and is otherwise the same experiment as the 413-station one with a bigger key set.
- **Published in:** `07-experiment-ledger.md` E-03's revive trigger and queue item 8, and `docs/1brc/handoff.md`'s `x-transfer` threads line — all in commits `f786d4e` and `5528b58`, both pushed.
- **What disproved it:** arithmetic over a file this study already generated and recorded. `02-baseline-data.txt` records `measurements-10k-stations-10m.txt` at **570,941,611 bytes for 10,000,000 rows**, so the synthetic 10k names cost **57.09 bytes per row** against the official set's 13.80. A billion of those rows is **57.09 GB**, not 13.8 GB. At the 725 MB/s the generator was measured at, that is **~79 s**, four times the published figure.
- **The larger error is not the 79 s.** At 57.09 GB the file is **2.22× this machine's 24 GiB of RAM**, where `measurements-1b.txt` is 53.5% of it, and its read floor alone is **3.12 s** at the 18.3 GB/s measured in `02-baseline.md` — three times over the study's whole target before any compute runs. So the file could not have answered the question it was queued for: no arm measured on it is comparable with the 1.742 s headline, and E-09's own mechanism (file size against RAM) says the ranking need not even carry. Holding **bytes** constant instead — 241.6M rows at 13.80 GB — reproduces the regime the 1b file established, and is what the dependent items actually want.
- **Consequence for the verdicts: none.** Nothing was measured on this file; every claim resting on it was already labelled parked, blocked or predicted. What changes is the queue: item 8 stops being the cheap unblocker three other items assumed, and it now carries a design choice (equal rows or equal bytes) that the round must make explicitly.
- **Why it happened:** the cost was estimated from the 13.8 GB the study measures everything on, without checking that the 10k key set's rows are 4.1× wider — and the recorded byte count that shows it had been sitting in `02-baseline-data.txt` since `env-data`. A generation estimate reads like bookkeeping, so nobody re-derived it.
- **Corrected in:** this commit, at both `07-experiment-ledger.md` sites, marked inline, with the derivation in the queue board. `docs/1brc/handoff.md`'s copy is corrected in this cycle's own handoff block rather than by editing the historical block, following C4.

## C6 — "deltas are only ever taken WITHIN one hyperfine invocation", as if that made arms comparable

- **Claimed:** that timing every arm of an experiment in ONE hyperfine invocation is what makes a delta trustworthy, so a percentage read off a single invocation at 1b is a result. It is the rule `experiment.sh` was built to enforce and it is stated in `07-experiment-ledger-data.txt:8` and in the harness's own header.
- **Published in:** `07-experiment-ledger.md` (the header's method rules and every row from E-02 to E-08), `07-experiment-ledger-data.txt:8`, `1brc/scripts/experiment.sh`'s comments, and `docs/1brc/handoff.md`'s `go-autoresearch-harness` block — commits `f786d4e`, `42b5b3d` and `4646edd`, all pushed.
- **What disproved it:** E-16, the null experiment. Eight arms of the SAME binary with the SAME flags, in one invocation, ranked **1.660 → 2.010 s, monotonically, +21.08%**, with user CPU rising 16.65% for identical work. One invocation is necessary and is not sufficient: within it, an arm's rank tracks the slot it ran in, at about 0.0302 s per slot. E-15 had already shown the same four arms swapping winner and loser when only their order changed.
- **The rule was half right, which is why it survived five rows.** Cross-invocation comparison really is worse (E-13's incumbent moved 11.17% between invocations), so the harness's insistence on one invocation was not wrong, it was incomplete. What was missing is that sustained load degrades the machine inside the invocation and recovers in the gaps between them — slot 1 measured 1.656 s at 32% battery and 1.660 s at 21%, eleven battery points and five minutes apart.
- **Consequence for the verdicts: three are no longer defensible and one kill nearly vanishes** (E-18, derived): E-06 (4 MiB buffer), E-07 (1<<17 buckets) and E-08 (`F_NOCACHE`) all sit inside the bias, two of them change sign under it, and E-03's split-table kill falls from 4.56% to 0.94%. E-02 (+19.18%), E-05 (+5.96%) and E-10 (+8.00% / +6.81%) survive with smaller margins. Nothing is retracted on a derivation: queue item 15 re-measures invocation B with the cooldown on and is the top of `go-opt-round-2`.
- **Corrected in:** this commit, at the ledger header's measurement rule, its experiment-budget formula and its incumbent-is-arm-1 rule, at E-06's, E-07's and E-08's verdicts, in the data companion and in the harness's own header. `docs/1brc/handoff.md`'s copy is corrected in this cycle's own handoff block rather than by editing the historical block, following C4 and C5. `experiment.sh` now sleeps 20 s before every timed run at 1b, stamps `NOT SLOT-CORRECTED` on any 1b file measured without it, and its `--self-test` pins both the default and the rejection of a non-numeric cooldown. The ledger header, the affected rows and the queue board are marked at their own sites.

## C7 — the correctness tax priced at "3-8% of compute" by inspection, measured at 18.2%

- **Claimed:** that the checks this binary runs so it rejects exactly what the reference rejects — `validTemp`'s four to six byte compares per row, and the dual-needle scan's four extra integer ops per word — cost **3-8% of compute**. Queue item 4, `07-experiment-ledger.md`, counted from the expression rather than measured, and labelled at the time as a prediction ("Prediction: 3-8% of compute").
- **Published in:** `07-experiment-ledger.md`'s queue item 4 and its board row, and `docs/1brc/handoff.md`'s `x-transfer` block, which carried the queue forward.
- **What disproved it:** E-21, the round-2 CPU profile. `validTemp` **alone** is **18.2% of samples** (2.58 s flat of 14.20 s), between two and six times the whole predicted range, and it is the second-largest consumer in the binary behind `indexDelim`. The contaminated earlier profile independently put it at 19.1%, so the figure does not rest on one run.
- **Why it happened:** four to six byte compares looked cheap next to a scan that touches every byte, and counting operations is not measuring them. What the count misses is that the compares are **per row** on data already in registers while the row is hot, i.e. exactly the position where an operation is *not* amortised by anything, and that they sit on the dependency chain between the parse and the table update. This is `lessons.md`'s standing rule ("arithmetic written in prose is never re-derived") in its performance form: a share of CPU is not derivable from an operation count, and this study has now been wrong in both directions on that — `04-asm-kernels.md` over-predicted a kernel by 50 points, and item 4 under-predicted a check by a factor of three.
- **Consequence for the verdicts: none is reversed, and one item is retired while another is created.** Nothing was ever measured against the 3-8% figure; it was a prediction ordering a queue. Item 4 is now **PRICED** and needs no trusting arm to price it, and its own escape clause ("if it is more, the shape of the check should change, not the contract") has fired, which is what boards **item 16** — establish the same format rejection from the 8-byte word the parse already loaded, instead of from four to six dependent byte compares, ceiling 18.2% of CPU, contract unchanged. Item 16 also records the version of that idea which does NOT work, because this review gate caught it in the first draft of the row: "check the integer instead of the bytes" fails, since the integer check (`inRange`) is already there on the same row and the byte check is what establishes that the bytes were a temperature at all.
- **Corrected in:** this commit, at queue item 4's prediction and its board row, with the measurement in E-21 and the replacement hypothesis as item 16. The `x-transfer` handoff block is left as written and corrected here, following C4, C5 and C6.
- **One site was missed, and it was the one a cycle reads first.** `docs/1brc/backlog.md`'s `go-opt-round-2-batch` line went on publishing the falsified mechanism — "item 16 (validate the temperature from the integer ...)" — for a full cycle after this entry was written, so the next cycle's instruction to build item 16 pointed at the version that does not work. Corrected when that ticket was split: the historical line is left as written and marked SPLIT, and the new `go-opt-round-2-item16` line carries the word-based mechanism together with an explicit note that the integer version is falsified. `lessons.md` now carries the general form, that a correction has to reach `backlog.md` and `spec.md` and not only the reports.

## C10 — "double-buffering each worker recovers the read stall, ceiling 20.4%, and it is the only board item that can reach 1.000 s"

- **Claimed:** that the 29-30% of worker wall E-20 measured blocked in `pread` was wall clock a per-worker fill-ahead goroutine could recover, at a ceiling re-derived four times as the baseline moved — **25%** at the transfer pass, **17.6%** at E-20, **19.1%** at E-25, **20.4%** at E-27 — and that after E-27 this was **the only item on the board that could reach the 1.000 s target**, landing on the 0.9812 s compute floor.
- **Published in:** `07-experiment-ledger.md` at queue item 14, at board row 14, and in E-27's closing "what it does NOT do" line; in `06-cross-disciplinary-transfer.md`'s C4 paragraph, its H-14 verdict line and its summary table; and in `docs/1brc/backlog.md`'s `go-opt-round-2-item14` line, which is the site a cycle reads before any report.
- **What disproved it:** E-29, the arm itself, in a bracketed slot-corrected invocation (bracket **0.989%** on wall, **0.116%** on user CPU, AC, preflight green), and **E-30, which re-ran it after the same cycle's review gate repaired a defect in the reader** — +0.82%/−0.08% of wall in a 0.905% bracket, the same verdict on shipped code. `-fill ahead` measures **1.232 s against 1.225 s and 1.213 s**, +0.57%/+1.57%, ranges overlapping both slots; user CPU is flat at −0.08%/+0.04%. The isolating pair is sharper than the incumbent comparison: `-fill sync` is the identical rewritten loop with the identical two buffers reading inline, so it differs from `ahead` by the fill goroutine ALONE, and the two land **0.24% apart on wall and 0.07% on user CPU**. The overlap did not underperform. It did nothing.
- **The ceiling arithmetic was never the error; the assumption under it was.** Every version of the ceiling was `(wall − floor)/wall` on a correctly measured floor, and every version was reported honestly as a ceiling rather than a forecast. What no version tested is that the gap it was reserving was *available* — E-20 measured 29-30% of PER-WORKER wall blocked in `pread` on a machine deliberately running 20 workers on 15 cores, and E-17 bought that oversubscription for the express purpose of covering one worker's read with another's fold. The overlap this item proposed to make explicit was already happening implicitly, at saturation. Parallel efficiency, which the prediction said would go 79.6% toward ~95%, measured **79.8% and 80.5% for the incumbent slots against 79.3% for `ahead`** — a 1.2-point spread across the whole invocation, in both directions.
- **Why it happened, and it is not the same failure as C7.** C7 was a claim that could have been checked by reading one call site. This one could only be checked by building the arm: the reasoning chain was sound at every published step, the underlying number (E-20's per-worker read share) is still correct, and `06-cross-disciplinary-transfer.md` even hedged it in writing — "because E-17's oversubscription already took *some* of the gap this figure was reserving". The defect is that a ceiling was carried forward four times, re-derived each time a baseline moved, and promoted to "the only item that can reach the target" without its load-bearing assumption ever being priced. **A ceiling is a hypothesis about a mechanism, not a property of the arithmetic; re-deriving it against a new baseline refreshes the number and re-states the assumption without testing it.**
- **Consequence: the board has no derived path to 1.000 s.** Item 14 is CLOSED, killed-on-numbers. The **19.85%** of wall between the 1.219 s bracket mean and the 0.9770 s compute floor is unexplained: not shard skew (E-20, 1.029-1.038), not the merge (0.34% of wall), and not read latency a per-worker prefetch can hide (this row). `go-opt-round-3` inherits that question rather than a mechanism, and `PARKED.md` P-05's revive condition is the one thing on the board that speaks to it.
- **One published number survives the re-measure and is confirmed rather than corrected:** E-24's 1 MiB read buffer. This item was supposed to invalidate it by changing the reader's syscall shape, and under the staged reader's constant-size reads at fixed offsets 512 KiB is **+5.76%** and 4 MiB **+6.57%** against 1 MiB, both disjoint.
- **Corrected in:** this commit, at queue item 14, board row 14 and E-27's "what it does NOT do" line in `07-experiment-ledger.md`; at the C4 paragraph, the H-14 verdict line and the summary table in `06-cross-disciplinary-transfer.md`; and at `docs/1brc/backlog.md`'s `go-opt-round-2-item14` line, per C7's own missed-site lesson. E-29 carries the measurement and the raw output is in `1brc/bench/2026-09-01T230802Z-H-14-board-item-14-double-buffered-workers.txt`. Following C4-C9, `docs/1brc/built.md` and `docs/1brc/handoff.md`'s historical blocks are left as written and corrected from this cycle's own block.

## C9 — "`indexDelim` is 33.5% of CPU, and 35.9% against E-25's smaller total"

- **Claimed:** that `indexDelim` is the biggest single pot on the board at **33.5% of CPU** (E-21), re-derived to **35.9%** against E-25's smaller user-CPU total, and that queue item 1 is therefore "where the CPU is". The same paragraph re-derived `(*table).update` to 17.1% and `memequal` to 6.2% the same way.
- **Published in:** `07-experiment-ledger.md` at E-21's measured line, in the queue board's staleness paragraph and in board item 1's row; and in `docs/1brc/backlog.md`'s `go-opt-round-2-items1and5` line, which is the site a cycle reads before any report.
- **What disproved it:** the re-profile that line itself demanded, run on the shipped default before anything was built. `indexDelim` is **20.36% and 17.73%** of samples over two runs, not 35.9%. The share collapsed because these are shares of a total that includes `syscall.rawsyscalln`, and that bucket moved from **15.7% to 54.03-56.66%** when E-24 changed the default read buffer from 4 MiB to 1 MiB. Profiling the same binary at `-buf 4096` puts the syscall back at **23.51%** and `indexDelim` at **31.27%**, which is E-21's reading again — so the binary did not change, the denominator did.
- **The share that survives is of the NON-syscall samples, and it is stable across both buffer settings:** 39.74% (E-21, back-derived), 40.88% (4 MiB, now), 40.90% and 44.29% (1 MiB, now). Applied to the 17.283 s of user CPU measured over three runs of the same configuration, that is **7.1-7.7 s**, against E-21's 6.21 s.
- **The syscall bucket is not CPU, which is what makes the compute denominator the honest one.** `rawsyscalln` takes 7.51 s of samples in a run whose whole measured **system** time is 1.52 s, 4.9x more than the process spent in the kernel at all, so at most a fifth of that bucket can be real. E-21 already measured pprof under-counting total CPU by 24.6% here and left the cause unidentified; darwin's process-wide `setitimer(ITIMER_PROF)` delivering SIGPROF to whichever thread is available, including one parked in `pread`, is the standing suspect and is a **hypothesis, not verified**.
- **Why it happened:** the re-derivation held each function's absolute cost constant and rescaled by the total, which is only sound if the COMPOSITION of the total is unchanged. E-24 had already changed it. The board's own staleness paragraph bounded the step it worried about — the two invocations' incumbents agreeing to 0.45% — and that bound is about the SIZE of the total, so it could not have caught a change in what the total is made of. The cycle that wrote it had also just written the lesson that names this exact risk ("every DERIVED figure on the board is a hostage to the baseline it was derived from"); it re-derived one arm's effect and missed that a different arm, two rows earlier, had moved the same baseline.
- **Consequence: item 1 is re-priced by two orders of magnitude and the board's ordering key is redefined.** What item 1 can remove is not `indexDelim`'s share; it is the SECOND load of the same word, which `-peek` attributes to `foldRows`'s own `littleEndian.Uint64` at **0.11 s of 6.39 s and 0.10 s of 9.37 s of compute — 1.07-1.72%**. `indexDelim` keeps the scan whatever the hash does. The item's original prediction, "small, the hash already reads only one word", was right, and the profile was read as overturning it when it never addressed it.
- **Corrected in:** this commit, at E-21's measured line, the board's staleness paragraph, board item 1's row and item 13's `memequal`/`update` targets, plus `docs/1brc/backlog.md`'s `go-opt-round-2-items1and5` line. E-26 carries the re-profile and the raw output is in `07-experiment-ledger-data.txt` §P. Following C4-C8, `docs/1brc/handoff.md`'s historical blocks stay as written and are corrected from this cycle's own block. **New standing rule, recorded in `lessons.md`:** a profile share is quotable only with the denominator it was taken against, and a share of a total containing the I/O bucket is not comparable across a change to the reader.

## C8 — six verdicts read off a contaminated invocation, and the derivation that was supposed to repair them

- **Claimed:** two things, and the second is the interesting one. First, the six verdicts invocation B produced: E-02 killing `-split cursor` at **+21.00%**, E-03 killing `-table split` at 413 stations at +4.56%, E-05 defending the branchless parse with scalar costing **+11.40%**, E-06 keeping 4 MiB, E-07 keeping 1<<17 buckets, E-08 keeping `F_NOCACHE` at +5.52%. Second, **E-18's repair of them**: that subtracting E-16's measured 0.0302 s per slot gives what those arms would have measured unbiased, leaving E-02's kill intact at +19.18% and E-03's at +0.94%.
- **Published in:** `07-experiment-ledger.md` at E-02, E-03, E-05, E-06, E-07, E-08 and E-18, in the standing results table, in its queue board, and in `docs/1brc/built.md` and `docs/1brc/handoff.md` for `go-v1-parallel` and `go-opt-round-1`.
- **What disproved it:** E-23, the re-measure those rows were already marked as owing, in a bracketed slot-corrected invocation (bracket 0.62%, user CPU flat at 3.29% and unordered). **Five of the six margins do not reproduce at all** — cursor lands at −0.56% to +0.06%, split at +0.87% to +1.49%, scalar at −1.12% to −1.73%, bits14 at −0.44% to −1.05%, pagecache at −0.43% to +0.19%, every one of them overlapping its incumbent. The sixth **reverses**: 1 MiB beats the 4 MiB default by 6.34%, disjoint, confirmed by E-24 in a second invocation to 0.27% and swept to a minimum.
- **The derivation failed worse than the rows it corrected.** E-18 predicted cursor at +19.18% and measured it at +0.06%, a 19-point miss, while its split figure (+0.94% against +1.49%) was close. So the linear per-slot model did not describe invocation B: it was not a conservative approximation of the contamination, it was the wrong shape for it. E-22 shows the same thing from the other side — a second contaminated invocation, this cycle, put its entire 27.37% excess in **system** time with user CPU flat and unordered, which no per-slot constant describes either.
- **Why it happened:** E-16 measured one contamination (sustained load degrading the machine monotonically across slots) and E-18 treated it as *the* contamination, so it modelled a different invocation's damage with the first one's constant and said so — it labelled itself DERIVED, not measured, and it named the extrapolation it was making. That label is why this is a correction and not a casualty: the row did the honest thing and was still wrong, because **a contaminated measurement carries no information about the size of its own contamination**. The general form is now in `lessons.md`: a bad invocation is re-run, never repaired by arithmetic.
- **Consequence for the verdicts: one reversal, three re-openings, two weakened keeps.** E-06 is REVERSED and the default buffer is now 1 MiB.
