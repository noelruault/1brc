## Gotcha found while verifying this data

Two of the 413 official station names contain a comma -- "Washington, D.C." and
"Flores,  Petén" (two spaces). The output format separates entries with ", ", so
the result line CANNOT be split on ", " to recover entries: "Washington, D.C."
splits into two. Byte-comparison against the reference output is the only sound
correctness check; any tool that parses the output line by splitting is wrong.

  $ grep -oE '\{"[^"]*"' 1brc/code/gen/stations.go | sed 's/{"//;s/"$//' | grep -nE '[,=]'
  124:Flores,  Petén
  396:Washington, D.C.

## Deviations from upstream's generator

1. Seeded PCG rather than ThreadLocalRandom, so the files are re-derivable.
2. Values are clamped into [-99.9, 99.9]. Upstream does not clamp; with sigma=10
   and station means in [-14.4, 30.5] the bound sits beyond 6 sigma, so the clamp
   is effectively never taken but makes conformance with README.md:422 structural
   rather than statistical. TestWriteClampsToLegalRange exercises it with an
   out-of-range station mean, since the official set can never reach it.
3. The 10k-station set is synthesised by this repo, not ported from upstream's
   CreateMeasurements3 (which slices names out of a concatenated corpus). It is a
   hash-pressure and key-count stressor, not a byte-compatible reproduction; see
   Synthetic10k in gen.go.

## Cold cache: not available, and what was used instead

`purge` requires sudo and this loop runs unattended (`sudo -n true` -> "sudo: a
password is required"), so a purged-cache measurement was not taken. Instead the
uncached path is measured directly with darwin's F_NOCACHE (fcntl F_NOCACHE=48,
set on the fd before reading): the kernel does not retain this descriptor's pages
in the unified buffer cache. This is not identical to a purged cache -- other
processes' pages stay resident -- and it is reported as "uncached", never "cold".

Evidence that F_NOCACHE actually took effect: three back-to-back 13.8 GB
uncached passes left free pages at 231,424 (3.53 GiB) and moved active by 25k
pages, where the same three passes WITHOUT it drove free pages to 3,699. A
no-op fcntl would have filled the cache.

## The arithmetic the target implies

  target                 1.000 s / 1e9 rows  =  1.00 ns/row  =  13.80 GB/s
  measured read floor    0.754 s             =  0.754 ns/row =  18.29 GB/s
  headroom               0.246 s             =  24.6% of the budget
  aggregate CPU budget   15 cores x 1.0 s    =  15.0 ns/row of core time
  read path's own CPU    30 ms user + 1075 ms sys = 1.10 ns/row of that 15.0
  left for the work      13.9 ns/row of core time, if parse overlaps I/O perfectly

  bufio.Scanner alone    11.30 ns/row single-threaded  ->  0.75 ns/row over 15 cores
                         = 75% of the entire wall-clock budget just to iterate lines
  naive reference        39.8 ns/row single-threaded   ->  2.65 ns/row over 15 cores
                         = 2.65x over budget with PERFECT scaling and zero I/O cost

## Benchmark confounds (spec.md:42)

Captured in the same session as the measurements above, once, after the runs rather
than sampled per run -- the amendment that requires this field landed mid-cycle. The
power state did not change during the session.

$ pmset -g batt | head -2
Now drawing from 'Battery Power'
 -InternalBattery-0 (id=23396451)	88%; discharging; 5:59 remaining present: true

$ uptime
14:59  up 1 day,  5:18, 19 users, load averages: 4.29 3.47 3.02

  ON BATTERY, so every figure in 02-baseline.md is PROVISIONAL per spec.md:42. macOS
  caps sustained CPU and SSD power on battery. The load average of 4.29 is this
  session's own tooling, not a quiet machine. What should be trusted from this report
  is the ORDERING of the I/O strategies and the order of magnitude of the floor, not
  any single millisecond figure. The headline is re-measured on AC at final-dod.
