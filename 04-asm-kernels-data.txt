## Name-length distribution of the two key sets

The 413 figures reproduce 03-technique-recon.md's independently, which is why
they are repeated here rather than cited.

The 10k figures are new, and they are why every 10k number in the report is
labelled a long-name stress case. 02-baseline-data.txt:115-118 already records
that gen.Synthetic10k is "a hash-pressure and key-count stressor, not a
byte-compatible reproduction" of upstream's CreateMeasurements3. What is
measured here is the third axis nobody had quantified: its names average 51.1
bytes against the official set's 8.0, and 68.9% of them exceed 32 bytes. So it
stresses name LENGTH harder than key count, and a kernel ranked on it is being
ranked on a distribution no real 1BRC input has.

  $ cd 1brc/code/asm && go test -run NameLengthDistribution -v ./...
  (TestNameLengthDistribution asserts these figures, so they are re-derivable by running the gate)
  413: n=413 mean=8.0 min=3 max=26  >8B=34.1%  >16B=1.0%  >32B=0.0%
  10k: n=10000 mean=51.1 min=1 max=100  >8B=93.2%  >16B=85.3%  >32B=68.9%

## The benchmark

  $ cd 1brc/code/asm && go test -count=1 -run '^$' -bench . -benchmem -benchtime 1s -count 10 ./...

Corpus: 524288 rows per key set, generated by gen.Write with a fixed seed, held
in memory with 16 bytes of readable slack past the end (the over-fetch every
kernel's 8- and 16-byte loads need). 413 corpus 7.2 MB, 10k corpus 32.5 MB.

ns/row is reported by the benchmark itself as elapsed / (passes x rows), so it
is immune to b.N bookkeeping. MB/s is over the corpus bytes.

### The deltas the report's verdicts rest on

Only WITHIN-benchmark deltas are quoted as findings: two loops with the same
shape and one thing varied. Across benchmarks the loop bodies differ in code
layout enough to move a tight loop by ~1 ns/row, which is the size of the
effects being measured, so cross-benchmark differences are not evidence.

## The control run — the harness's own floor

The report's smallest verdict is H6 interleaved, a 0.165 ns/row margin. A margin
that size has to be shown to be the kernel rather than the code layout of the
closure it was measured in, so the harness was measured against itself: two
byte-identical copies of each shift loop, in different closures, benchmarked in
the same invocation. Whatever they disagree by is the floor under every margin
in this report.

So closure placement moves these loops by 0.001-0.002 ns/row. H6's margins are
0.513 and 0.165 ns/row, which clear that floor by 83x (smallest margin against
the largest floor) to 513x (largest margin against the smallest floor).

### Run-to-run drift is a different and much larger thing

BenchmarkMaskName/shift/single measured 2.267 ns/row in the main run above and
2.102 in this one, 7.9% apart, from identical code. The main run's load average
moved 3.43 -> 5.03 while it ran; this one's moved 2.28 -> 2.51. That is why no
number here is ever compared across invocations, and why the report quotes only
within-run, same-shape pairs.

### Every verdict-bearing pair is disjoint over all ten runs

Full-range spread within one benchmark's ten runs is 0.8% (ParseTemp/branchless/413) to
15.6% (Tokenize/batch/413), so quoting a median difference alone would not
establish an ordering. The stronger check is separation: for every verdict in
the report, the winner's SLOWEST of ten runs is still faster than the loser's
FASTEST of ten. No run of any pair overlaps, so no verdict here depends on
which run was picked.
