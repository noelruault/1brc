## Probe 1 — arm64 has no PMOVMSKB. What replaces it?

$ cat neon_probe.c   # in this study's history; the body is reproduced in the report
$ clang -O2 -arch arm64 -o neon_probe neon_probe.c && ./neon_probe
input           : Hamburg;12.0
Abha;-2
shrn4 mask      : 0x00000000f0000000
shrn4 first ';'  : 7  (ctz>>2)
shrn4 any        : 1
vmaxvq any ';'   : 1
vmaxvq any '#'   : 0
swar  mask      : 0x8000000000000000
swar  first ';'  : 7  (ctz>>3)
shrn4 first NL   : 12 (mask 0x000f000000000000)
swar  NL in [0,8): no (mask 0x0000000000000000)
all 16 positions: ctz(mask)>>2 == byte index, 4 set bits per match
exit=0

  Verified: vceqq_u8 + vshrn_n_u16(...,4) packs 16 byte-comparisons into a 64-bit
  word at 4 bits per byte, and ctz(mask)>>2 is exactly the index of the first match
  for all 16 positions. SWAR over the same data agrees on the ';' at index 7, and
  misses the newline at index 12 because it only sees 8 bytes -- which is the whole
  argument for the 16-byte window on the name scan.

## Probe 3 — does the Go stdlib already do this?

$ grep -n "0x40100401" $GOROOT/src/internal/bytealg/indexbyte_arm64.s
	// Magic constant 0x40100401 allows us to identify which lane matches
	MOVD	$0x40100401, R5

$ grep -rl VCMEQ $GOROOT/src | grep '\.s$'
/usr/local/go/src/internal/bytealg/count_arm64.s
/usr/local/go/src/internal/bytealg/equal_arm64.s
/usr/local/go/src/internal/bytealg/indexbyte_arm64.s

  Verified: bytes.IndexByte, bytes.Count and bytes.Equal are ALREADY hand-written
  NEON on arm64. IndexByteString works in aligned 32-byte chunks and builds a 64-bit
  syndrome with 2 bits per byte (indexbyte_arm64.s:7-14), using 0x40100401 =
  (1<<0)+(4<<8)+(16<<16)+(64<<24) to give each lane a distinct bit. This is the same
  family as probe 1's 4-bit-per-byte narrowing, at 32 bytes per iteration instead of
  16. It explains 02-baseline's result that bytes.Count runs at memory bandwidth.

## Probe 4 — does merykitty's parse actually produce the right number?

Reimplemented in Go from the arithmetic described in the entries' comments, then run
over EVERY legal temperature (-99.9 to 99.9, all 1999 values in tenths), checking
both the value and the returned next-line offset:

$ cd /tmp/parseprobe && go test -v ./...
=== RUN   TestSwarParseCoversEveryLegalTemperature
--- PASS: TestSwarParseCoversEveryLegalTemperature (0.00s)
PASS
ok  	parseprobe	0.362s

The function that passed:

	func swarParse(word uint64) (tenths int64, next int) {
		dotPos := bits.TrailingZeros64(^word & 0x10101000)
		shift := 28 - dotPos
		signed := int64(^word<<59) >> 63
		designMask := ^(signed & 0xFF)
		digits := (int64(word) & designMask << uint(shift)) & 0x0F000F0F00
		absValue := (digits * 0x640a0001 >> 32) & 0x3FF
		return (absValue ^ signed) - signed, dotPos>>3 + 3
	}

  Exhaustive over the legal domain, so this is not a spot check: 1999 of 1999 values
  parse to the right tenths, and every returned offset equals the field length
  including its newline. It needs an 8-byte load from the start of the temperature
  field, i.e. up to 3 bytes of over-fetch past the newline on the shortest field
  ("0.0\n"), which is the constraint the chunk boundaries have to respect.

## Probe 5 — how long are the station names, really?

The 16-byte hash window and the 8-byte SWAR word are both bets about name length, so
the distribution was computed from the key table rather than assumed. Names are
extracted from the 413 (name, mean) pairs in code/gen/stations.go and measured in
BYTES, not runes, because that is what the scan sees.

$ python3 -c '<extract {"name" from stations.go, len(name.encode()) for each>'
entries: 413
byte length: min 3 max 26 mean 8.0
>8 bytes : 141/413 = 34.1%
>16 bytes: 4/413 = 1.0%
longest: Las Palmas de Gran Canaria 26

  An earlier draft of 03-technique-recon.md asserted "88.6% of names are longer than
  8 bytes" as the rationale for H2. That number was invented and is wrong by a factor
  of 2.6. Measured: 34.1%. The correction weakens H2's prediction, which now says the
  margin may go either way, and it also shows thomaswue's 16-byte hash window has a
  slow path that fires on 1.0% of rows rather than never.
