2. THE TABLE ENTRY SIZE — measured, and it corrects a number published five times
================================================================================

Throwaway test dropped into 1brc/code/go as zz_sz_test.go, run, and deleted:

    func TestSizes(t *testing.T) {
        fmt.Println("entry", unsafe.Sizeof(entry{}))
        fmt.Println("bits17 entries bytes", (1<<17)*unsafe.Sizeof(entry{}))
        fmt.Println("bits17 hashes bytes", (1<<17)*8)
        fmt.Println("bits14 entries bytes", (1<<14)*unsafe.Sizeof(entry{}))
    }

$ go test -run TestSizes -v ./...
entry 48
bits17 entries bytes 6291456
bits17 hashes bytes 1048576
bits14 entries bytes 786432

So on darwin/arm64 `entry` is 48 bytes, not 32: key []byte (24) + min int32 (4) + max int32 (4)
+ sum int64 (8) + count int32 (4) = 44, padded to 48 by the 8-byte alignment of sum.

  1<<17 entry array  = 6.00 MiB   (published as 4 MiB at five sites — see CORRECTIONS.md C4)
  1<<17 hash array   = 1.00 MiB   (published correctly)
  1<<14 entry array  = 768 KiB    (published as 512 KiB in E-07's prediction)
  split-array ratio  = 6.00 / 1.00 = 6x, not the "quarter" published in E-03 and table.go

Derived from the two facts together, and this is the transfer that uses them: fifteen shards
each own a 6.00 MiB entry array, so the fifteen tables are 90.0 MiB of live allocation and
the five Super cores share 16 MiB of L2 while the ten Performance cores share 8 MiB. A single
shard's table does not fit either L2. Only ~413 of its 131,072 slots are ever touched, which
is why E-07 still measured the BIG table winning; the point for the transfer report is that
the array's SIZE and the working set's size are two different numbers and only the second one
was ever argued about.

4. THE ARITHMETIC IN THE REPORT, RE-DERIVABLE
================================================================================

Heterogeneous static split, the bound in candidate C1. Let the fast class run at rate r_f and
the slow class at r_s, five and ten cores, and let the whole file be one unit of work.

  equal split:        every worker gets 1/15; the wall clock is set by the slowest,
                      T_equal = (1/15) / r_s
  weighted split:     ranges proportional to rate; all workers finish together,
                      T_weighted = 1 / (5*r_f + 10*r_s)
  ratio               T_equal / T_weighted = (5*r_f + 10*r_s) / (15*r_s) = (1/3)*(r_f/r_s) + 2/3

  r_f/r_s = 1.0  ->  1.000   (homogeneous: weighting buys nothing, as it must)
  r_f/r_s = 1.1  ->  1.033
  r_f/r_s = 1.3  ->  1.100
  r_f/r_s = 1.5  ->  1.167
  r_f/r_s = 2.0  ->  1.333

DERIVED, not measured: it assumes the work is perfectly divisible, the file is uniform, and
compute is the binding constraint. r_f/r_s for this machine is UNKNOWN and measuring it is
step one of the experiment.

Idle-core arithmetic, quoted from 07-experiment-ledger.md's "Where v1 stands" and not re-measured
here: 19.657 s of user CPU over 1.742 s of wall clock is 11.28 cores busy of 15, 75.2%.
If double buffering (candidate C5) closed the whole gap and nothing else changed, the same CPU
work over 15 busy cores would be 19.657/15 = 1.310 s. That is a CEILING on that one change under
an assumption the report states; it is not a prediction that it will be reached.
