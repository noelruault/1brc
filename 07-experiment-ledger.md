# 07 — Experiment ledger

Append-only. One row per experiment, each with the idea, the prediction made BEFORE the run, the measured result, and a verdict. A row is never edited once its verdict is written; a superseded number gets a new row and a `CORRECTIONS.md` entry. Raw output and every command: [`07-experiment-ledger-data.txt`](07-experiment-ledger-data.txt).

**Verdict vocabulary** (`PARKED.md`'s, plus the two that keep code): `KEEP` (the default now), `KILLED-on-numbers` (records the number AND the baseline it was measured against, because numbers move), `PARKED` (not disproved, no number yet), `SPLIT` (the answer depends on the input and both arms stay).

**The measurement rule this ledger enforces**: a delta is only ever taken between two arms of the SAME hyperfine invocation, because the identical binary measured 1.667 s in one invocation and 1.717 s in another. Cross-invocation numbers are recorded and never subtracted. **[CORRECTED, C6: necessary, not sufficient.** E-16 ran eight IDENTICAL arms in one invocation and they rose monotonically by 21.08%. A 1b invocation must also **sleep 20 s before every timed run** (`experiment.sh -c`, now the default there) and **name the incumbent first and last**, or its arms are ranked by their slots. Rows E-02 to E-08 predate the fix; E-18 prices what that did to them.**]**

## The loop this ledger runs — and where it came from

The optimization rounds run an autoresearch loop: **hypothesis queue → one experiment → one metric → keep/kill → ledger row → the queue is re-ranked**. The adaptation is [`1brc/scripts/experiment.sh`](scripts/experiment.sh), which runs exactly one experiment and refuses the runs that this study has already learned produce uninterpretable numbers.

The primary sources are this repo's own prior art, because it has run this loop before and the traps it walked into are recorded: [`shapes-image-file-format/AUTORESEARCH.md`](../shapes-image-file-format/AUTORESEARCH.md) (the running log plus a ranked bottleneck queue, both in one handover file), [`shapes-image-file-format/METHODOLOGY.md`](../shapes-image-file-format/METHODOLOGY.md) (a pre-run and a post-run checklist), [`shapes-image-file-format/07-method-what-worked.md`](../shapes-image-file-format/07-method-what-worked.md) (the practices that caught real errors) and [`quantization/00-methodology.md`](../quantization/00-methodology.md) (piece-level against integration-level benchmarking). The secondary source is https://github.com/karpathy/autoresearch, fetched 2026-09-01 (see the data companion): an agent edits one file, `train.py`, trains for exactly five minutes, scores one metric, `val_bpb`, and keeps or discards.

**Four things transplant, and each one is a check in the harness.**

- **A fixed experiment budget** — karpathy's is five minutes of training per attempt, which buys ~12 attempts an hour. Ours is one hyperfine invocation on the 1b file: N arms at five runs plus a warmup, so an N-arm experiment costs about `N × 6 × 1.75 s` of timing — 31.5 s for three arms — plus a per-arm correctness pass. **[CORRECTED, C6: the 20 s cooldown is now mandatory at 1b and it dominates the budget — `N × 6 × 21.75 s`, so 130 s for three arms and 17 minutes for eight. The incumbent also appears twice, first and last, so an N-knob experiment costs N+2 arms.]** That is the same trade for the same reason, and it lands on this ledger's binding rule for free, because all the arms are in one invocation.
- **One edit surface.** karpathy's agent only edits `train.py`. Every hypothesis here has instead become a **flag on one binary** — `-split`, `-table`, `-io`, `-parse`, `-kernel` — which is `METHODOLOGY.md` §1.1's "add a pricing function; never replace the baseline" in the form this problem takes. The incumbent is arm 1 of every invocation, so `AUTORESEARCH.md`'s "reproduce the baseline before changing anything" happens inside the run rather than against a published number. **[CORRECTED, C6: arm 1 AND the last arm. Being first is the most flattered slot there is, so an incumbent measured only there is the one arm the invocation cannot judge.]**
- **A predicted number before the run.** `07-method-what-worked.md`: "An investigation that predicts 5 KB and measures 21 KB has learned something; one that only measures has produced a number nobody can interpret." `experiment.sh -p` is mandatory and must contain a digit; a knob-turn with no mechanism is allowed only as `-p 'sweep: <why>'`, which is E-06's precedent and labels the row honestly.
- **A clean negative is a result.** `AUTORESEARCH.md`: "If it does not: add the log entry anyway with the number that killed it." Three of the eleven rows here are `KILLED-on-numbers` and a fourth, E-03, is a `SPLIT` whose 413 half is killed; E-11 is a method rule extracted from E-10's kill, and E-09 from the seven arms that disagreed across two file sizes.

**Two things deliberately do NOT transplant.**

- **The automatic keep/discard.** karpathy's loop compares one scalar and decides. Ours cannot: the verdict vocabulary above has four outcomes and `SPLIT` exists because E-03 and E-05 both depend on the input, so a scalar comparison would have thrown away a flag that is still the right default on one of the two key sets. `experiment.sh` measures, gates and pre-fills the row; **a human or an agent writes the verdict**, and `- **Verdict:**` is emitted blank on purpose.
- **Iterating on a cheaper proxy.** The obvious speedup is to run the loop on the 100m file at a tenth the cost. E-09 measured that it does not rank arms — seven arms, seven disagreements — so `experiment.sh` refuses any file but 1b unless `--mechanism-only` is passed, and then stamps `NOT A VERDICT` on the output. Mechanism evidence at 100m is welcome; verdicts from it are not.

One rule from `quantization/00-methodology.md` is already load-bearing here and needs no new machinery: piece-level and integration-level are **two different measurements**, and E-11 is what happens when a piece-level number is quoted as an integration-level one.

**The two mechanisms measured so far move different quantities, and the table above is what separates them.** E-24 took 6.4% of wall clock without touching user CPU (18.541 s at 4 MiB, 18.604 s at 1 MiB): it bought parallel efficiency, 77% → 82.1%, and closed none of the compute gap. **E-20 corrects the reading of that last sentence, not its arithmetic.** "47% of the wall clock is the unavoidable read" invites the conclusion that the other 53% is the target's problem; the measured compute floor says the read is not the constraint at all. 18.53 s of CPU over 15 cores is 1.235 s of unavoidable *compute*, which is 480 ms MORE than the read floor it would hide behind, so at perfect overlap the read costs nothing and the binary still misses 1.000 s. **E-25 is the first arm to move that floor, and it does not clear it.** 17.279 s over 15 cores is 1.152 s, so 152 ms of per-core compute still has to go before the target is even reachable at perfect parallelism, and the read floor is 398 ms below it rather than 480. 17.28 ns of CPU per row against the 15.00 ns budget: the shape of the problem is unchanged, the margin is 15.2% instead of 23.5%.

**E-27 clears it, and that inverts the shape of the problem the three paragraphs above describe.** 14.718 s over 15 cores is **0.9812 s**, so the compute floor is **18.8 ms BELOW the 1.000 s target** and the per-row CPU is **14.72 ns against the 15.00 ns budget, 1.9% under**. Every sentence in this ledger of the form "the target sits below the compute floor" was true when written and is now superseded: the binary spends little enough CPU per row to finish in under a second at perfect parallelism, and it does not, because it runs at **79.6% efficiency**. **The lever is no longer CPU per row; it is the 20.4% of wall clock between 1.233 s and the floor**, which is scheduling — item 14's territory — and it is the first time that item's ceiling lands under the target rather than on it. The margin is thin enough to say plainly: 18.8 ms of headroom on a 5-run reading is not a promise that 1.000 s is reachable, only that nothing measured now forbids it.

## Rows

### E-01 — 8 bytes of station name are enough to hash on (H4)

- **Idea:** hash the first 8 bytes of the name, masked at the separator, and let a full `bytes.Equal` resolve collisions.
- **Prediction** (`03-technique-recon.md`, H4): zero unresolved collisions on the 413 set, manageable on the 10k set.
- **Measured** (`05-go-techniques.md`, a static computation over both key sets, no benchmark): 412 distinct 8-byte prefixes for 413 names — one collision, `Alexandra`/`Alexandria` — and 413 distinct 16-byte prefixes. 10,000 distinct 8-byte prefixes for the 10k set.
- **Verdict: KEEP.** Shipped as `kernel.go:hashWord`. The one collision costs one extra probe on one station.

### E-02 — a shared cursor over 2 MiB segments beats a static equal split (H1)

- **Idea:** hand each worker 2 MiB at a time from an atomic cursor, so the Performance/Efficiency core asymmetry cannot leave the static split's slowest shard setting the wall clock.
- **Prediction** (H1): dynamic wins by **≥5%**; the static split's last shard idles the fast cores.
- **Measured, invocation B (1b):** static **1.667 s** [1.643-1.685], cursor **2.017 s** [1.976-2.058]. Cursor is **21.0% SLOWER**, disjoint over five runs each. At 100m (invocation A) the two are indistinguishable: 152.9 ms [150.9-155.5] against 153.6 ms [152.3-154.3], overlapping ranges.
- **Verdict: KILLED-on-numbers** against static-split-at-1b = 1.667 s in invocation B. **[CORRECTED, C8: RE-OPENED. E-23 re-measured `-split cursor` slot-corrected at −0.56% to +0.06%, overlapping the incumbent: the 21% is gone entirely, and so is E-18's derived +19.18%. Cursor is no longer killed — it is indistinguishable at 5 runs, which is not the same as harmless, so the flag stays and the arm goes back on the queue.]** The prediction was not just wrong in size, it was wrong in direction. The mechanism is not established; the measured symptom is that cursor mode does 21% more wall clock for the same 19 s of user CPU, which points at 15 workers re-entering the same file at unpredictable offsets instead of streaming one contiguous range each. **Revive trigger:** a run where the static split's shards demonstrably finish more than 5% apart, which nothing here measures yet.

### E-04 — mmap the whole file (H7)

- **Idea:** the universal choice in the public 1BRC corpus — map 13.8 GB and let the page-fault path do the reading.
- **Prediction** (H7, written after `02-baseline.md` measured mmap losing 5-9× on a *scan*): parallel `pread` stays ahead once aggregation runs too, and `madvise(MADV_WILLNEED)` is the rescue that might change it.
- **Measured, invocation C (1b, own anchor):** anchor `pread` **1.717 s** [1.687-1.759], mmap **9.693 s** [9.619-9.827], mmap **+ `MADV_WILLNEED` 10.782 s** [10.702-10.893]. mmap is **5.6× slower** and the named rescue makes it **11% worse still**. System time tells the story: 18.4 s for mmap against 2.3 s for `pread`. At 100m — a 1.4 GB file that fits in RAM — mmap is *marginally faster* than `pread` (151.2 ms against 152.9 ms, overlapping) and `madvise` is already 18% worse than the default arm (19.6% worse than mmap without it).
- **Verdict: KILLED-on-numbers** against `pread`-at-1b = 1.717 s in invocation C. ### E-09 — the meta-result: a 100m run does not rank a 1b run

- **Idea:** iterate on the 100m file, which is 10× cheaper, and promote the winners.
- **Measured:** **seven arms, seven disagreements.** Every arm above that separates at 1b either inverts at 100m (H3 parse, buffer size, table bits, `F_NOCACHE`) or vanishes into overlapping ranges (H1 cursor, H5 layout, H7 mmap, where mmap is 5.6× slower at 1b and *marginally faster* at 100m).

### E-10 — the batch tokenizer, end to end (queue item 2)

- **Idea:** `04-asm-kernels.md`'s largest measured win. Scan a window, drain both needles from one compare, aggregate from the drain, rather than rescanning from each row's first byte. Built two ways so the assembly call could be priced: `-kernel batch-neon` calls `asm.DelimMask32` once per 32 bytes, `-kernel batch-swar` drains both needles from each 8-byte word in pure Go and makes no call at all. Neither materialises a token stream; both fold straight into the table, which is strictly less memory traffic than the benchmarked kernel did.
- **Prediction:** the report handed this forward as the shape to build, at **−40.4% / −40.7%** on the official key set, and named it "the single most load-bearing untested assumption in this report". `05-go-techniques.md`'s 1.93 ns Plan 9 call cost predicted `batch-neon` would beat `batch-swar`, the window being ~2.3 rows wide.
- **Measured, invocation D (1b, 413 stations, 5 runs, one hyperfine invocation):** per-row `row` **1.684 s** [1.659-1.713], `batch-swar` **1.849 s** [1.819-1.883], `batch-neon` **1.859 s** [1.805-1.897]. Percentages are relative to the arm being replaced, which here is the incumbent `row`: `batch-swar` costs **9.8% MORE** and `batch-neon` **10.4% MORE**, both disjoint (`row`'s slowest run, 1.713 s, beats either batch arm's fastest, 1.819 s and 1.805 s). The two batch arms do NOT separate from each other. ### E-25 — the format check folded into the word the parse already loaded (queue item 16, CLOSES it)

- **Idea:** `validTemp` establishes the shape `-?\d{1,2}\.\d\n` by indexing `b[0]`..`b[5]` behind a three-way `switch` on `next`, and `next` varies per row, so the switch is unpredictable and the byte loads are dependent. `parseTempBranchless` already holds those bytes as one 64-bit word. `parseTempWord` folds the whole rejection into that word: the `.` and `\n` at their fixed offsets from the dot lane, a SWAR digit test on the two lanes bounding the digit run plus the lane above the dot, the sign byte when the parse read one, and the digit COUNT — one accumulator, `bad == 0`, and no branch inside the check. The clause "can never go below the compute floor" still holds and is now a promise rather than a limit.**]

### Added by the round-2 profile (E-20, E-21)

16. **Validate the temperature's FORMAT from the word the parse already loaded, instead of from four to six dependent byte compares.** `validTemp` is **18.2% of measured CPU** (E-21), the second-largest consumer in the binary. What it checks is the shape `-?\d{1,2}\.\d\n` that `parseTempBranchless` "assumes and cannot itself check" (`kernel.go:121`), by indexing `b[0]`..`b[5]` and testing digit-ness and literal `.` and `\n` positions, one `switch` arm per field length.

    **The obvious version of this idea is wrong, and it is written down here so it is not tried twice.** "Replace the byte checks with an integer range test on the tenths the parse produced" does not work, because that test already exists and already runs on every row: `table.go:134` is `if next == 0 || !validTemp(field, next) || !inRange(v)`, and `inRange` is the range test. The two are not redundant — `inRange` bounds the VALUE, `validTemp` establishes that the bytes were a temperature at all, and the branchless parse will happily return an in-range integer from malformed input like `1x.5` or `--1.5`. Dropping `validTemp` for `inRange` would accept rows the reference rejects, and **no generated corpus can catch it**, because every generated row is well-formed: this is the third appearance of the trap `lessons.md` records under "no corpus can express it".

    **So the hypothesis is a cheaper implementation of the same rejection, not a cheaper rejection.** `parseTempBranchless` already loads the field as one 8-byte word (`binary.LittleEndian.Uint64`) and already derives the `.` position from it with `TrailingZeros64`; the format check re-reads the same bytes individually afterwards. Testing digit-ness of several bytes at once on the word that is already in a register is the standard SWAR form (`(w - 0x30…) | (w + 0x46…)` masked, one AND and one compare against the dot mask the parse computed), which would replace a chain of dependent byte loads and branches with a few word-level ops. **The contract does not move**: the binary must reject byte-for-byte what `gen.Aggregate` rejects.

    **Prediction:** the ceiling is the measured 18.2% of CPU (compute floor 1.235 s → 1.010 s) and it is NOT reachable, because the check is replaced rather than removed; a SWAR form that costs a quarter of the current one would return ~13%, and anything at or above 8% is worth keeping. Unlike most of this board the risk is on the correctness side, so it ships with a rejection test per malformed class — bad digit, doubled sign, missing dot, missing `\n`, two decimals, out-of-range — each asserted against `parseTempScalar`'s independent answer and against the reference, before anything is timed.

    **CLOSED — E-25, KEPT: −4.97% of wall and −6.33% of user CPU, disjoint, new best 1.424 s.** The 8% bar was missed and the arm was kept anyway, with the reasoning in the row. The "quarter of the cost" mechanism is falsified: the new check costs 65.2% of the old. The correctness demand was met by exhaustive differential sweep rather than by a case list — 2,000,000 six-byte fields over the alphabet the shape is built from, two over-read fillers, every verdict compared against both `parseTempBranchless`+`validTemp` and `parseTempScalar` — which contains every named malformed class and ten mutants, all caught.

## The queue board — state, cost, and the command

The two lists above hold the hypotheses and their reasoning. This is their **state**, and it is what `go-opt-round-1` dispatches from; the numbering is theirs, never reassigned, because E-10 cites "queue item 2" and a renumbered queue would silently re-point it. Thirteen of the fourteen seeded items are open, which satisfies the harness ticket's floor of ten.

**Re-ordered by the round-2 profile, and the ordering rule changed with it.** Until E-20 the queue was ordered by "the size of the gap each could close" with the gap read as wall clock; the compute floor of 1.235 s against a 1.000 s target makes **share of measured CPU** the ordering key, because a mechanism that does not remove CPU cannot reach the target no matter what it does to scheduling. So the top of the board is now the four items that cut CPU per row, ordered by the share E-21 measured, and H-14 — still the largest single mechanism, at a 17.6% ceiling then and **19.1% against E-25's smaller wall** — sits below them because at its ceiling it lands on the compute floor, 1.24 s then and **1.152 s now**, and never below it. [**SUPERSEDED by E-27, and the ordering rule inverts with it: the compute floor is now 0.9812 s, BELOW the 1.000 s target, so "cuts CPU per row" no longer selects for reaching the target and H-14 — 20.4%, landing at 0.9812 s — moves to the TOP of the board. Round 3 is ordered by wall clock recoverable from scheduling, and the CPU items are worth what they are worth on their own.**]

**The shares this board is ordered by were re-derived once and the re-derivation was wrong; E-26 measures them instead.** [**CORRECTED, C9.**] The falsified paragraph read: E-21 profiled a binary whose total was 18.53 s of user CPU, E-25 removed 6.33% of it without touching the other functions, so every surviving item's share ROSE against a smaller total — `indexDelim` 33.5% → 35.9%, `(*table).update` 15.9% → 17.1%, `memequal` 5.8% → 6.2%, bounded by the two incumbents agreeing to 0.45%. **What that bound could not catch is that the total changed COMPOSITION rather than size:** E-24 had already moved the default read buffer 4 MiB → 1 MiB, and `syscall.rawsyscalln` went 15.7% → 54.03-56.66% with it, so every other share is compressed against a denominator that is mostly not compute. Measured now on the shipped default, `indexDelim` is **17.73-20.36%** of samples, and profiling the same binary at `-buf 4096` puts it back at 31.27%.

**So the board is ordered by share of the NON-syscall samples, which is the only figure that survived the buffer change** — `indexDelim` **40.9-44.3%**, `parseTempWord` 17.7-21.7%, `(*table).update` 12.4% flat, `memequal` 7.2-8.7%, `foldRows` itself 6.6-8.8%, `merge` 2.0%, all agreeing to within 3.4 points across three profiles at two buffer sizes (E-26). Against the 17.283 s of user CPU measured over three runs, `indexDelim` is **7.1-7.7 s**. The syscall bucket is excluded because it cannot be CPU: it holds 7.51 s of samples in a run whose whole measured system time is 1.52 s.

**Runnable now** means every arm is already a flag on the shipped binary, so the experiment costs only its own timing — about `N × 6 × 1.75 s` for N arms at 1b, so 31.5 s for a three-arm row, plus a correctness pass per arm. **Needs code** means an arm has to be built and gated first, and the ledger row cannot be opened until it is.

**Item 8 is not the cheap unblocker three other items assume it is, and the reason is a design question, not a cost one.** Derived from the recorded size of `measurements-10k-stations-10m.txt` (570,941,611 B for 10,000,000 rows, `02-baseline-data.txt`): the 10k key set costs **57.09 bytes per row** against the official set's 13.80, because the synthetic names are longer. Every arm would land three times over target before any compute, so nothing measured there could be compared with the 1.742 s headline. Holding **bytes** constant instead gives **241.6M rows** at 13.80 GB, which reproduces the memory regime the 1b file established and is the file items 9, 10 and 12 actually want. The round must pick one knob and say which; generating both is 79 s and 19 s of a generator that reproduces byte-for-byte from its seed, and 329 GB of disk is free.
